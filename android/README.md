# Android Runtime Design (Pixel / Samsung)

This document defines the Android equivalent of `metal_infer/infer.m`.

On macOS we have a single Objective-C + Metal binary (`infer.m`) that does:
1. token loop orchestration,
2. router + top-k expert selection,
3. SSD streaming (`pread`) of selected experts,
4. GPU kernels for MoE/attention,
5. sampling/logits output.

On Android, we should keep the same flow but swap platform layers:

- **Metal API** ➜ **Vulkan compute**
- **Objective-C runtime** ➜ **C++17 NDK runtime**
- **macOS file/cache behavior** ➜ **Android/Linux pread + mmap hints**

---

## 1) Target module layout

```
android/
  README.md                        # this file
  CMakeLists.txt                  # NDK build entrypoint (shared library)
  infer_android.h                  # public C API similar role to infer.m entrypoints
  infer_android.cpp                # token loop + scheduler + JNI-safe API
  jni/com_flashmoe_FlashMoeNative.cpp  # JNI bridge for Kotlin/Java callers
  kotlin/FlashMoeNative.kt         # Kotlin wrapper used by Android app layer
  vulkan_backend.h                 # Vulkan backend abstraction
  vulkan_backend.cpp               # Vulkan init, pipeline cache, descriptor sets
  shaders/
    dequant_matvec.comp
    swiglu.comp
    rmsnorm.comp
    moe_combine.comp
    attention.comp
```

The `infer_android.cpp` file is the **control plane** equivalent of `infer.m`:
- parse model config,
- load manifests,
- run per-layer scheduling,
- stream selected experts with `pread`,
- collect runtime I/O telemetry via `fm_android_get_stats`,
- expose simple `init`, `generate`, `shutdown` entrypoints.

---

## 2) Runtime pipeline (Android equivalent of `infer.m`)

For each decoded token:

1. **Token state update**
   - Maintain current token state in runtime.
2. **Router pass**
   - Compute gating logits and choose Top-K experts.
3. **Expert streaming (storage -> staging buffers)**
   - Use `pread()` from packed layer files (`layer_XX.bin`) using exact offsets from `layout.json`.
   - Use small reusable staging buffers to avoid allocator churn.
4. **Expert compute**
   - Run attention + dequant matvec + SwiGLU + down projection + MoE combine + RMSNorm through backend kernel hooks.
   - Backend first attempts a Vulkan compute plugin (`libflashmoe_vulkan_kernels.so`) and falls back to CPU kernels if unavailable.
5. **Sampling**
   - Convert hidden state into next token logits/token id.

This preserves the same architecture and file-I/O contract as desktop while keeping compute portable during early Android bring-up.

---

## 3) Device targets and constraints

### Pixel (Adreno)
- Prefer subgroup-size-agnostic kernels (avoid hardcoding wave size assumptions).
- Keep descriptor set updates minimal; use persistent descriptor pools.
- Validate with sustained 10+ minute decode runs for thermal behavior.

### Samsung (Adreno or Mali)
- Expect higher driver variance; compile shaders at startup and persist pipeline cache.
- Keep fallback code paths for devices lacking optional Vulkan features.
- Start with `VK_KHR_shader_float16_int8` optional path; keep fp32 fallback.

---

## 4) Buffering strategy

Use three classes of buffers:

1. **Persistent model buffers**
   - non-expert tensors loaded once.
2. **Per-layer transient expert buffers**
   - reused ring of staging + device-local buffers sized for K experts.
3. **Scratch buffers**
   - activation/intermediate tensors reused across layers.

Rules:
- no full-model expert caching in RAM,
- per-token keep only selected experts resident,
- free/recycle transient buffers immediately after each layer.

---

## 5) File I/O strategy

- Keep packed file contract generated by `repack_experts.py` and validated by `validate_packed_experts_layout.py`.
- `layout.json` provides `expert_size`, component offsets, and per-layer file names.
- Use positional reads:
  - `offset = expert_idx * expert_size + component.offset` (plus layer file base).
- Use a small thread pool for concurrent reads of selected experts.

On Android this is still Linux VFS backed, so `pread` semantics are portable from macOS logic.

---

## 6) API shape (JNI-friendly)

Define a C ABI so Kotlin/Java can call it directly via JNI:

```c
int fm_android_init(const char* model_dir, const char* model_config_path);
int fm_android_generate(const int* input_tokens, int input_len, int max_new_tokens,
                        int* output_tokens, int output_cap);
int fm_android_get_stats(fm_android_stats_t* out_stats);
void fm_android_shutdown(void);
```

Then expose Kotlin wrappers for:
- `init(modelDir)`
- `generate(prompt, maxTokens)`
- streaming callback per token.

The initial JNI bridge is implemented in:
- `android/jni/com_flashmoe_FlashMoeNative.cpp`
- `android/kotlin/FlashMoeNative.kt`

Minimal NDK build usage from an Android app module:

```gradle
externalNativeBuild {
  cmake {
    path file("src/main/cpp/android/CMakeLists.txt")
  }
}
```

## 7) Implementation order (practical)

1. ✅ Implemented: `infer_android.cpp` control loop with manifest/config load + per-layer expert streaming.
2. ✅ Implemented: real decode math path with per-layer QKV attention, KV cache, MoE feed-forward, RMSNorm, and vocabulary logits projection.
3. ✅ Implemented: backend runtime selection (`Vulkan plugin -> CPU fallback`) for dequant/SwiGLU/combine/RMSNorm/attention/softmax.
4. Next: add shader package (`android/shaders/*.comp`) and hook the plugin into app packaging for device-side acceleration.
5. Validate parity against macOS output on short prompts (use `tools/parity_check.py` for token and router trace comparisons).
6. Optimize per-device (Pixel first, then Samsung).

---

## 8) Success criteria for first Android experiment

- Runs Qwen3.5-35B-A3B token generation on at least one Pixel and one Samsung device.
- No OOM for a 128-token decode window.
- Stable >5 minute run without Vulkan device loss.
- Reports per-token latency breakdown for I/O vs compute.
